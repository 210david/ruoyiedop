# 业务附件自动纳入统一知识检索 — 开发方案（简化实施版）

| 项 | 内容 |
|---|---|
| 版本 | v1.0（简化实施版，2026-11-09） |
| 适用环境 | EDOP（RuoYi 体系、私有化单库、单租户），**用户数与附件数据量都很少** |
| 技术栈 | 沿用现有 Spring Boot + MySQL + MyBatis + POI/PDFBox + 现有 embedding 配置，**不引入 MQ、向量库、新中间件** |
| 阅读对象 | 后端 / 前端 / 联调测试 |

> 本版只写「怎么改代码」。评审、签字、门禁、验收人、指标签收、沟通节奏等过程性内容一律不在本文范围。

---

## 0 要做成什么样

业务模块（投标、项目等）上传附件后，**不需要再去 AI 知识库页面二次上传**，就能在问答里被检索到并带来源回跳。

四条硬口径：

1. 上传后**自动纳入**，不改上传交互；可在附件列表单条排除/撤回纳入。
2. **报价件、涉密件只登记、不检索**：不切片、不向量化、不外送 OCR，问答搜不到，但列表里能看到「已登记」。
3. **扫描件／盖章件要能搜到图里的字**：普通扫描件可送外部 OCR；涉密件跳过。
4. **权限沿用现有附件权限**（可见／可预览／可下载三级），不新建权限模型。

---

### 0.1 满足需求只要这 6 件事

| # | 做什么 | 说明位置 |
|---|---|---|
| 1 | 两张**现有表**加几个字段（来源、状态、版本），不建新表 | §3 |
| 2 | 业务模块保存附件后，调一次 `AttachmentIndexService.register()` | §4.1、§5 |
| 3 | `register()` 复用现有 POI/PDFBox 抽取 → 500 字切片 → embedding → 写入知识库 | §4.1 |
| 4 | 检索 SQL 按模块＋现有权限过滤并加 `LIMIT`，业务附件就能被搜到、结果带来源 | §4.4 |
| 5 | 点击来源回跳沿用现有附件权限；**上传交互一律不改** | §4.5、§6 |
| 6 | 已确认的两条口径：普通扫描件走 OCR 能搜到字；报价／涉密件只登记、不检索 | §4.2、§4.3 |

> 其余章节（换版留历史行、7 个读取出口、定时任务、前端状态标签、自检清单）都是**这 6 件事的实现说明与防踩坑提示，不是额外要做的项目**，现场没碰到就可以后做或不做。
>
> 只有 §4.4 里两个补丁必须带上：过滤放在 Top-K **之前**、未配置 embedding 时**不要把历史切片排除**。这两处不改，功能本身是坏的（曾出过配置切换后检索全空的事故），与「严谨」无关。

## 1 为什么可以简单做（设计取舍）

| 现实条件 | 对应取舍 |
|---|---|
| 用户少、附件少 | **同步处理**即可，不需要 Outbox／事件驱动／Worker 线程池；单文件解析慢就顺手改一个 2 线程异步，状态字段不变 |
| 私有化单库 | 不需要索引版本别名、回滚点、跨租户隔离；出问题直接查库、单条重跑 |
| 已有 RAG 链路 | 复用 `ai_knowledge_doc` / `ai_knowledge_chunk` 两表与 `AiKnowledgeServiceImpl` 的抽取／切片／embedding 代码，**不重建** |
| 表结构可小改 | **零新增表**：把「只登记」「失败」「已失效」全部用 `ai_knowledge_doc` 上的状态字段表达 |
| 权限已有 | 查询时按「当前用户可见的 biz_id 列表」过滤即可，不做 ACL 标签快照 |

**明确不做**（避免过度设计，别再往里加）：MQ/Outbox、状态机＋重试死信、索引版本别名与原子切换、全量对账双路径、三段 `trace_id`、覆盖率 2×2 看板、四维灰度＋熔断、故障注入演练、评测集／负向用例集、SLA 与告警体系。

## 3 数据库改动（全部是 ALTER，不建新表）

### 3.1 `ai_knowledge_doc` 加字段

```sql
ALTER TABLE ai_knowledge_doc
  ADD COLUMN source_ref     VARCHAR(200) NULL COMMENT '来源唯一键 模块:业务ID:文件ID',
  ADD COLUMN source_module  VARCHAR(32)  NULL COMMENT 'pjm/bid/...',
  ADD COLUMN source_type    VARCHAR(32)  NULL COMMENT '附件表/散字段/统一入口',
  ADD COLUMN biz_id         VARCHAR(64)  NULL COMMENT '业务单据ID',
  ADD COLUMN file_id        VARCHAR(64)  NULL COMMENT '附件记录ID或URL哈希',
  ADD COLUMN content_hash   VARCHAR(64)  NULL COMMENT '文件内容哈希，去重与换版',
  ADD COLUMN doc_version    INT          NOT NULL DEFAULT 1 COMMENT '版本，换版递增',
  ADD COLUMN superseded_by  BIGINT       NULL COMMENT '被哪个新版doc_id替代',
  ADD COLUMN biz_status     VARCHAR(20)  NOT NULL DEFAULT 'VALID' COMMENT 'VALID/VOID/REVOKED',
  ADD COLUMN index_status   VARCHAR(24)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/INDEXED/NOT_INDEXABLE/FAILED',
  ADD COLUMN fail_reason    VARCHAR(500) NULL,
  ADD COLUMN exclude_reason VARCHAR(64)  NULL COMMENT 'QUOTE_OR_SENSITIVE 等',
  ADD COLUMN sensitivity    VARCHAR(16)  NOT NULL DEFAULT 'NORMAL' COMMENT 'NORMAL/SENSITIVE',
  ADD COLUMN file_missing   CHAR(1)      NOT NULL DEFAULT '0',
  ADD UNIQUE KEY uq_source_ref (source_ref),
  ADD KEY idx_module_status (module, index_status),
  ADD KEY idx_biz (source_module, biz_id);
```

`ai_knowledge_chunk` **不加字段**，通过 `doc_id` 关联 doc 表取版本与状态即可（少一处改造）。`chunk.content` 继续作文本兜底快照。

### 3.2 `pjm_project_attachment` 加字段（换版用）

```sql
ALTER TABLE pjm_project_attachment
  ADD COLUMN doc_version   INT          NOT NULL DEFAULT 1,
  ADD COLUMN biz_status    VARCHAR(20)  NOT NULL DEFAULT 'VALID',
  ADD COLUMN superseded_by BIGINT       NULL;
```

### 3.3 存量兼容

现有字段与 `status(0/1/2)` 全部保留；存量行新字段走默认值，补一条回填即可，**不重建表、不停机**：

```sql
UPDATE ai_knowledge_doc SET index_status = 'INDEXED' WHERE status = '0' AND index_status = 'PENDING';
```

## 4 后端改造

### 4.1 新增一个注册服务（唯一新增类）

`ruoyi-ai` 下新增 `AttachmentIndexService`，对外只有一个方法：

```java
public void register(String sourceRef, String module, String bizId,
                     String fileId, Path filePath, String operator)
```

流程（**同步、同事务、不抛异常到上传链路**）：

1. 按 `source_ref` 查 `ai_knowledge_doc`；命中且 `content_hash` 相同 → 直接返回（幂等，重复上传不产生重复切片）。
2. 计算 `content_hash`；按 `attachment_type`＋`source_module` 判密级（§4.2）。
3. **报价／涉密件** → 写一行 `index_status='NOT_INDEXABLE'`、`exclude_reason='QUOTE_OR_SENSITIVE'`，**不读文件内容、不切片、不向量化、不外送**，返回。
4. 其余 → 调用现有抽取／切片／embedding 链路（把 `AiKnowledgeServiceImpl` 的 `extractText(MultipartFile)` 提取为可按 `Path` 调用的公共方法，逻辑不变，500 字切片／50 字重叠）。
5. 成功 → `index_status='INDEXED'`；失败 → `index_status='FAILED'`＋`fail_reason`，**只记状态，不抛出**，业务上传照常成功。
6. 删除 doc 与 chunk 现在是两条独立 SQL，改成**同一事务**（或先删 chunk 再删 doc 的补偿顺序），避免孤儿切片。

> 数据少，同步够用；若上传明显变慢，把第 4 步包进一个固定 2 线程的 `ThreadPoolExecutor.submit()`，状态字段与重跑方式都不变。

### 4.2 密级初筛（10 类，不做审批流）

按 `attachment_type` 字典实际值域建一张映射（配置化，别硬编码在代码里）：

| 值 | 名称 | 初筛 |
|---|---|---|
| 1 | 招标文件 | NORMAL |
| 2 | 投标文件 | NORMAL |
| 3 | 项目图纸 | NORMAL |
| 4 | 项目保险 | NORMAL |
| 5 | 合同协议 | **SENSITIVE**（报价／金额条款常见） |
| 6 | 技术方案 | NORMAL |
| 7 | 会议纪要 | NORMAL |
| 8 | 检查报告 | NORMAL |
| 9 | 影像照片 | NORMAL（走 OCR） |
| 10 | 其他资料 | NORMAL |

`SENSITIVE` → 只登记、不识别、不向量化、不外送。`attachment_type` **只是初筛信号，不是密级事实，也不是状态机**；判错时在附件列表提供「改密级」入口，改完重新触发注册并留一条操作日志。

### 4.3 文件读取与格式分派（处理存储双轨）

统一入口写盘是**加密**的，AI 知识库自行写盘是**明文**的，解析链路必须兼容两种：

```java
byte[] plain = readPlainBytes(path);   // 读前 7 字节判断 "EDOPENC" 魔数
                                       // 命中则复用 FileUploadUtils 中的解密实现
                                       // （若为 private，提取为 public decrypt(Path)）
```

| 输入 | 处理 |
|---|---|
| `pdf/docx/md/txt` 有文本层 | 复用 POI / PDFBox |
| 扫描版 PDF、图片（普通件） | 外部 OCR 服务 → 文本 → 同一条切片链路 |
| 扫描版 PDF、图片（涉密件） | 已在 §4.1 第 3 步拦截，不会走到这里 |
| 无文本层、格式不支持、解密失败 | `index_status='NOT_INDEXABLE'` 或 `FAILED`＋原因，**绝不静默产生空切片** |

### 4.4 检索 SQL 改造（最重要的一处）

废止「把全部切片捞到应用层再算分过滤」。改 `AiKnowledgeDocMapper.xml`：

```sql
SELECT c.chunk_id, c.doc_id, c.chunk_index, c.content, c.embedding,
       d.doc_name, d.module, d.source_ref, d.biz_id, d.doc_version
FROM ai_knowledge_chunk c
JOIN ai_knowledge_doc d ON d.doc_id = c.doc_id
WHERE d.status = '0'
  AND d.index_status = 'INDEXED'
  AND d.biz_status = 'VALID'
  AND d.superseded_by IS NULL
  AND (d.module = #{module} OR d.module = 'platform')
  AND d.biz_id IN
      <foreach collection="visibleBizIds" item="id" open="(" separator="," close=")">#{id}</foreach>
LIMIT #{candidateLimit}
```

要点：

- `module` **改为必传**；`/qa` 不传 `module` 时直接返回空结果并记一条日志，不再走「无过滤全库切片」。
- `visibleBizIds` 由现有业务权限查询得出（用户少、单据少，直接查 ID 列表即可）。
- `LIMIT` 放在候选集阶段，`TOP_K=5` 不再用应用层 `subList` 截断。
- **未配置 embedding 时去掉任何 `embedding IS NOT NULL` 条件**，保留关键词降级通道——历史上正是「只查有向量的切片」导致配置切换后历史文档检索全空。
- `selectDocByName` 按文件名查重停用，改 `source_ref` 唯一键＋`content_hash`。

### 4.5 读取出口统一鉴权（不设单一拦截点）

确证存在的读取出口，逐个接入同一个 `AttachmentAuthService.canView(user, sourceRef)`：

| # | 出口 |
|---|---|
| 1 | `GET /common/download` |
| 2 | `GET /common/download/resource` |
| 3 | `GET /common/file/access`（`/profile/**` 由 nginx 代理到此） |
| 4 | `GET /common/file/preview` |
| 5 | `GET /ai/knowledge/download/{docId}`（原样返回原文件字节） |
| 6 | `GET /ai/knowledge/preview/{docId}`（原文件转 PDF） |
| 7 | 其余 `MultipartFile` 旁路写盘对应的读取点，联调时按出口清单补齐 |

检索结果返回 `source_ref`＋`doc_name`＋状态；点击来源时**再鉴权一次**（索引侧过滤只是粗筛，查询时点实时权限为准）。403 时写一条 `log.warn` 带用户／`source_ref`／原因即可，不做计数指标。

### 4.6 换版：留历史行、只返最新有效版

改 `PjmProjectServiceImpl` 级联保存（原逻辑是逻辑删旧行＋插新行，旧行业务不可见）：

```
保存附件时：
  不 UPDATE 覆盖原行，也不 DELETE 旧行
  → 旧行置 biz_status='SUPERSEDED'、superseded_by=新行ID
  → 插入新行 doc_version = 旧版 max + 1、biz_status='VALID'
  → 调 register() 为新行建索引，并把旧 doc 标 SUPERSEDED
```

配合 §4.4 的 `superseded_by IS NULL` 与 `biz_status='VALID'`，检索天然只返最新有效版。作废／撤回／`del_flag='2'` 走 `BizStatus=VOID/REVOKED`，同样不再命中、不再被引用。

### 4.7 一个定时任务就够

用 Spring `@Scheduled`，每天凌晨扫一次（数据量少，全表扫无压力）：

- 检查 `status='0'` 的 doc 对应源文件是否存在 → 不存在置 `file_missing='1'`、`index_status='NOT_INDEXABLE'`，避免「命中却打不开」；
- 列出 `index_status='FAILED'` 的行，运维视图提供「单条重跑」按钮，重跑即再调一次 `register()`。

不做双向差集对账、不做事件兜底、不做周期多路径扫描。

## 5 接入点（在哪调 `register`）

| 附件形态 | 接入位置 |
|---|---|
| 结构化附件表（如 `pjm_project_attachment`） | 对应 Service 保存成功后，遍历 `attachmentList` 调 `register` |

> 不做全局上传切面：会重复注册、且拿不到业务单据 ID 与权限上下文。

## 6 前端改动（少量）

1. 附件列表加一个状态小标签：`已纳入 / 索引中 / 不支持 / 已登记（不检索） / 失败`，并提供单条「排除纳入」「撤回纳入」「改密级」「重跑」。
2. 检索结果来源卡片显示文件名＋状态＋「打开原件」按钮；打不开时给一句「当前无权访问该附件」。
3. 空结果给可解释文案（未纳入／索引中／格式不支持／权限不足／已失效）。
4. **上传组件、上传交互一律不改。**

## 7 配置

```yaml
attachment:
  index:
    enabled: true
    whitelist: pdf,docx,md,txt,jpg,jpeg,png,pdf-scan
    ocr-url: ${AI_OCR_URL:}          # 普通扫描件外送 OCR；涉密件不走
    sensitive-types: 5               # 按 attachment_type 字典实际 10 类配置
    exclude-types: 5                 # 与 sensitive-types 一致即可，只登记
    candidate-limit: 200
ai:
  embedding-url: ${AI_EMBEDDING_URL:}
  embedding-key:  ${AI_EMBEDDING_KEY:}
  embedding-model: ${AI_EMBEDDING_MODEL:}
system:
  upload:
    path: D:/EDOP/uploadPath         # 统一根路径，与历史事故直接相关，变更须同步迁移
```

统一根路径＋版本化文件名（如 `{bizId}/{fileId}_v{docVersion}.{ext}`），换版另存不覆盖；不做内容寻址。

## 9 联调自检（10 条，联调时顺手过一遍即可，不走验收流程）

1. 上传一个 PDF，稍等后问答能命中并带来源。
2. 重复上传同一文件，不产生重复切片与重复 embedding 调用。
3. 报价／涉密件上传后，问答搜不到、列表显示「已登记」，且**没有发生任何外部调用**。
4. 投标扫描件、盖章件能搜到图里的字，来源能回跳定位。
5. 低权限账号既搜不到越权内容，点来源也打不开原件。
6. 单据作废／附件撤回后不再命中，也不再被引用。
7. 换版后只返最新有效版，旧版不命中。
8. 删掉源文件后，巡检能标失效，不出现「命中却打不开」。
9. embedding 配置切换后，历史文档仍能检索（关键词降级可用）。
10. 解析失败或 OCR 不可用时，**业务上传本身仍然成功**，附件列表能看到失败原因并可重跑。
