## ⚠️ 开发纪律与跨模块改动管控（强制，用户 2026-11-07 明确要求）

**以下四条为强制纪律，任何阶段开发均须遵守：**

1. **严格遵循现有开发规范与代码风格**：开发前先读 `design/unified-development-standards.md` 及相关页面风格指南，代码结构、命名、注释风格与现有实现保持一致。
2. **不得修改或影响任何已开发完成的现有功能**：现有功能行为零变更是底线。
3. **跨模块改动必须先申报、获批后方可动手**：如实现需要改动其他业务模块代码，必须**先列出具体修改点及原因**，与用户确认并获批后方可进行改动；未经确认不得修改。

## 一、背景与目标

### 1.1 背景

EDOP 平台已形成 20 个 Maven 模块的完整业务体系（WMS/DMS/MK/PMS/QMS/MMS/HR/FIN/BI 等），但与外部产品（钉钉、企业微信、用友、金蝶）的集成能力为零，告警通道虽预留了钉钉/企微扩展点（`AlertManager` 注释）但未实现。

### 1.2 目标

建立统一的第三方集成能力层，一期范围：

| 优先级 | 目标 | 说明 |
|---|---|---|
| P0 | **钉钉考勤数据同步**（核心场景） | 钉钉打卡结果 → HR 考勤模块 `biz_hr_attendance_record`，复用现有 `importAttendance` 原始数据导入链路 |
| P0 | **钉钉打样** | 机器人告警 + 工作通知 + 待办 + 通讯录同步，跑通统一连接器抽象 |
| P1 | 企业微信 | 复用一期抽象层，预计 3-5 天完成 |
| P2（暂缓） | 用友 / 金蝶 | 版本碎片化严重（U8/T+/U8C 三套体系、老 K3 WISE vs 云星空），待有真实客户场景再启动 |

> 2026-11-07 需求确认：用户明确一期核心诉求为"钉钉打卡考勤数据集成到人力资源考勤模块"，已核实 HR 模块具备完整承接基础（见 §3.7），场景可行性定级为高。

### 1.3 分期策略（用户已确认）

**先用钉钉一个连接器把抽象接口验证到位，后续企微近乎复制粘贴，用友金蝶二期再接。** 一期只锁定钉钉，不为想象中的复杂度提前设计。

## 二、可行性分析结论

### 2.1 现状盘点（对集成有利的已有基础）

| 已有基础 | 位置 | 对本模块的意义 |
|---|---|---|
| SPI 扩展先例：`AlertChannel` 告警通道 | `ruoyi-framework/alert/` | 阶段 0 快赢的现成插口，`AlertAspect` 切面已有真实流量 |
| SPI 扩展先例：`IModuleStatsProvider` + Spring List 注入 | `ruoyi-common/stats/` | 统一连接器接口用同构模式，零业务依赖（bi 模块已验证） |
| HTTP 工具 | `ruoyi-common/utils/http/HttpUtils.java` | `sendPost(url, param, contentType)` 支持 JSON POST，无需引额外框架 |
| fastjson2 | 全项目通用 | 构建请求 JSON / 解析响应 |
| Quartz 调度 | `ruoyi-quartz` | 通讯录同步等定时任务直接接入 |
| AES 加密工具 | `ruoyi-common/utils/sign/` | AppSecret 数据库密文存储 |
| Redis | framework | access_token 缓存（钉钉/企微 token 均有有效期） |

### 2.2 产品对接难度分级

| 产品 | 对接方式 | 难度 | 一期决策 |
|---|---|---|---|
| 钉钉 | 开放平台企业内部应用（access_token + 回调）+ 自定义机器人 webhook | ★☆☆ | ✅ 一期实现 |
| 企业微信 | 开放平台 API，与钉钉高度同构（corpid/secret/agentid） | ★☆☆ | 二期，抽象层预留 |
| 金蝶 | 金蝶云星空 WebAPI 标准；老 K3 WISE 需中间库/组件 | ★★☆~★★★★ | 暂缓 |
| 用友 | YonBIP/YonSuite 开放 API；U8/T+/U8C 三套体系碎片化 | ★★★ | 暂缓 |

**结论：难度不在代码，在客户环境版本碎片化。** 钉钉/企微文档完善、接口标准，一期完全可行。

## 三、总体架构设计

### 3.1 模块规划

新建 `ruoyi-integration` Maven 模块，符合规范 1.1 命名与 1.2 接入步骤：

- **依赖方向合规**（规范 1.1 / 6.1）：`ruoyi-integration` 仅依赖 `ruoyi-common` + `ruoyi-system`，位于依赖链末端，不被业务模块依赖；业务模块需要发消息时通过 common 中定义的接口 + Spring 注入调用（与 bi 模块消费 `IModuleStatsProvider` 同构，方向相反但机制相同）。
- Controller 层挂到 `ruoyi-admin` 聚合（回调入口免鉴权路径 + 管理端接口）。

### 3.2 统一连接器接口（定义在 ruoyi-common）

新增包 `com.ruoyi.common.integration`：

```java
/** 统一外部连接器接口，参照 IModuleStatsProvider 的 SPI 模式 */
public interface IExternalConnector
{
    /** 连接器类型标识：dingtalk / wecom / ... */
    String getConnectorType();

    /** 连接器是否已配置可用 */
    boolean isConfigured();

    /** 发送工作通知（收件人 userIds 为平台内部用户，由连接器负责映射） */
    SendResult sendWorkMessage(IntegrationMessage message);

    /** 创建待办（可选实现，默认不支持） */
    default SendResult createTodo(IntegrationTodo todo) { return SendResult.unsupported(); }
}
```

DTO：`IntegrationMessage`（标题/内容/收件人/跳转链接）、`IntegrationTodo`、`SendResult`（success/errorMsg）。

收集方式：`ruoyi-integration` 内 `IntegrationManager` 通过 Spring 注入 `List<IExternalConnector>` 收集所有连接器实现，调用方按 `connectorType` 路由。**业务侧永远只依赖接口，不知道钉钉细节。**

### 3.3 数据库设计

```sql
-- 第三方应用凭据配置（平台级，admin 管理）
CREATE TABLE integration_app_config (
    config_id       BIGINT       NOT NULL AUTO_INCREMENT COMMENT '配置ID',
    connector_type  VARCHAR(32)  NOT NULL                COMMENT '连接器类型(dingtalk/wecom/yonyou/kingdee)',
    app_name        VARCHAR(64)  NOT NULL                COMMENT '应用名称',
    app_key         VARCHAR(128) DEFAULT NULL            COMMENT 'AppKey/CorpID',
    app_secret      VARCHAR(512) DEFAULT NULL            COMMENT 'AppSecret(密文存储，不回显)',
    agent_id        VARCHAR(64)  DEFAULT NULL            COMMENT 'AgentId(钉钉/企微应用ID)',
    callback_token  VARCHAR(128) DEFAULT NULL            COMMENT '回调Token(密文)',
    callback_aes_key VARCHAR(512) DEFAULT NULL           COMMENT '回调加密AES Key(密文)',
    status          CHAR(1)      DEFAULT '0'             COMMENT '状态(0启用 1停用)',
    create_by       VARCHAR(64)  DEFAULT '',
    create_time     DATETIME     DEFAULT NULL,
    update_by       VARCHAR(64)  DEFAULT '',
    update_time     DATETIME     DEFAULT NULL,
    remark          VARCHAR(500) DEFAULT NULL,
    PRIMARY KEY (config_id),
    UNIQUE KEY uk_connector_app (connector_type, app_name)
) ENGINE=InnoDB AUTO_INCREMENT=1 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='第三方应用配置表';

-- 同步/调用日志（审计与重试依据）
CREATE TABLE integration_sync_log (
    log_id        BIGINT       NOT NULL AUTO_INCREMENT COMMENT '日志ID',
    connector_type VARCHAR(32) NOT NULL                COMMENT '连接器类型',
    biz_type      VARCHAR(64)  NOT NULL                COMMENT '业务类型(work_msg/todo/contact_sync/callback)',
    direction     CHAR(1)      DEFAULT '1'             COMMENT '方向(1外发 2回调)',
    biz_key       VARCHAR(128) DEFAULT NULL            COMMENT '业务关键字(单号/手机号等)',
    status        CHAR(1)      DEFAULT '0'             COMMENT '状态(0成功 1失败)',
    error_msg     VARCHAR(1000) DEFAULT NULL           COMMENT '失败原因',
    cost_ms       INT          DEFAULT NULL            COMMENT '耗时(毫秒)',
    create_time   DATETIME     DEFAULT NULL,
    PRIMARY KEY (log_id),
    KEY idx_type_time (connector_type, create_time)
) ENGINE=InnoDB AUTO_INCREMENT=1 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='集成调用日志表';
```

安全设计（遵循 AI 配置规范 1.1.1 同款原则）：
- **密钥密文存储、接口不回显、留空沿用**（编辑时不填 = 保持原值）。
- 平台级配置，仅 admin/管理员角色可见，不做部门数据权限（豁免归属，规范 3.5 统计/配置类同款处理）。

### 3.4 菜单与权限（规范 3.4 M/C/F 三级）

- 目录 M：**系统集成**（挂系统管理同级或系统工具下）
- 菜单 C：应用配置（`integration/config`）、调用日志（`integration/log`）
- 按钮 F：应用配置的 query/add/edit/remove/testConnection（连接测试按钮，发一条测试消息验证凭据）

SQL 脚本放 `sql/integration.sql`（规范 7）。

### 3.5 定时任务（规范 2.9）

- `integrationContactSyncTask`（`@Component("integrationContactSyncTask")`，放 `task/` 目录）：钉钉/企微通讯录全量同步 → 落 `sys_user`（按手机号/userId 映射，**只补全外部 ID 映射，不覆盖平台已有权限与角色**），每日凌晨执行，幂等。

### 3.6 回调入口

- `IntegrationCallbackController`：`/integration/callback/{connectorType}` 免鉴权路径（SecurityConfig 白名单）。
- 钉钉/企微回调验签：`callback_token` + `callback_aes_key` 解密验签；URL 校验事件（check_url）首次注册时响应加解密样例。
- 内网客户无公网回调时的兜底：关键事件走 Quartz 轮询模式（一期只做通讯录轮询，消息回调二期完善）。

### 3.7 场景一：钉钉打卡考勤 → 人力资源考勤模块（一期核心场景）

#### 3.7.1 用户故事与价值

- **作为 HR 专员**，我希望员工在钉钉上的打卡结果自动同步到平台考勤记录，以便不需要再人工导出 Excel 导入。
- **作为 HR 主管**，我希望考勤统计口径始终由平台统一计算，以便考勤机与钉钉双数据源不打架、月报对得上。
- **价值**：消除人工导出导入环节（现 `HrAttendanceImportDTO` 导入为手工操作），考勤数据 T+1 自动到账。

#### 3.7.2 承接基础（已核实，2026-11-07）

| 现有基础 | 位置 | 集成角色 |
|---|---|---|
| 考勤机原始数据导入服务 `importAttendance()` | `HrAttendanceRecordServiceImpl` | **核心复用点**：已实现按员工+日期分组、按时间排序、最早为上班/最晚为下班、updateSupport 幂等更新 |
| 原始打卡中间格式 | `HrAttendanceImportDTO` | 钉钉打卡结果转换目标，无需新建 DTO |
| 打卡来源字典 `hr_clock_source` | 字典数据 | 新增"钉钉"字典值，区分数据来源 |
| 迟到/早退/考勤状态/班次 | `HrAttendanceRecord` + `biz_hr_shift` | 全部复用平台现有口径，不由钉钉判定 |
| 月度汇总 / 补卡 / 请假出差联动 | `HrAttendanceMonthly` / `HrClockRepair` 等 | 不受影响，自动继承 |

#### 3.7.3 钉钉侧对接设计

- **前置条件**：钉钉企业内部应用 + 开通考勤数据读取权限点（Attendance）；AppKey/AppSecret 存 `integration_app_config`。
- **拉取接口**：`attendance/list`（打卡结果）为主，`attendance/listRecord`（原始记录）备用；约束：单次时间跨度 ≤7 天、单批 ≤50 人，需分批分段。
- **人员匹配（可配置策略，2026-11-07 实现）**：参数 `integration.dingtalk.matchType` 三种策略——`mobile`（手机号，默认）/ `jobNumber`（钉钉工号 jobNumber ↔ 员工工号）/ `auto`（工号优先、手机号兜底）；参数设置页实时切换、任务执行时读取，无需重启；**切换策略只影响未匹配绑定**，已匹配（含人工绑定）不自动重跑，防止冲掉既有绑定；绑定表 `match_type` 记录实际命中策略（auto_mobile / auto_jobNumber / manual）便于审计。未匹配员工进入异常清单（绑定列表页核对后人工绑定），不静默丢弃。
- **同步任务**：`integrationDingtalkAttendanceTask`（task/ 目录，`@Component` 命名）每日凌晨拉取昨日打卡 → 转 `HrAttendanceImportDTO` → 调 `importAttendance(updateSupport=true)`；首次上线支持指定起始日期分段回溯（7 天一段）。
- **幂等性**：导入服务本身支持同员工+同日期更新覆盖，任务重跑安全。
- **手动补拉**：考勤记录页增加"从钉钉同步"按钮（F 权限控制），支持按日期范围手动补拉，走同一服务方法。

#### 3.7.4 Non-goals（明确不做）

- 不做钉钉排班/班次同步（平台班次口径为准，钉钉仅提供打卡时间）。
- 不做钉钉"迟到/早退/旷工"判定结果的直接采用（平台统一计算，保证口径唯一）。
- 不做反向写入（平台不回写打卡数据到钉钉）。
- 不做钉钉审批流（请假/补卡仍在平台内走平台流程）。

#### 3.7.5 验收指标

| 指标 | 基线 | 目标 |
|---|---|---|
| 考勤数据到账时效 | 人工导入（月/周级） | T+1 凌晨自动同步 |
| 匹配成功率 | — | ≥98%，未匹配进入异常清单可人工绑定 |
| 任务幂等重跑 | — | 重跑后记录数与打卡值不变 |
| 与现有导入结果一致性 | — | 同一原始数据经钉钉通道与 Excel 通道导入结果完全一致 |

## 四、一期实施计划（钉钉打样）

### 阶段 0：快赢——钉钉机器人告警通道（0.5~1 天）

不建新模块、不动现有代码结构，直接验证端到端链路：

- 新增 `ruoyi-framework/alert/DingTalkAlertChannel.java`：实现 `AlertChannel`，`@PostConstruct` 自注册进 `AlertManager`（webhook 未配置则不注册，零行为变更）。
- 支持自定义机器人 **加签**（HmacSHA256 + Base64 + URLEncoder）。
- 配置项（`application.yml`，默认关闭）：

```yaml
alert:
  dingtalk:
    webhook:            # 机器人 webhook 地址，留空则通道不启用
    secret:             # 加签密钥，留空表示无密钥机器人
    enabled: false
```

- **验收标准**：`@Alert` 注解触发的系统告警（`AlertAspect` 现有流量）同步出现在钉钉群；webhook 留空时行为与现状完全一致。
- 价值：立即见效，且为正式连接器提供真实联调经验。

### 阶段 1：模块地基（2 天）

- `ruoyi-integration` 模块骨架 + 根 pom 注册 + admin 聚合。
- common 包 `com.ruoyi.common.integration`：接口 + 3 个 DTO。
- `integration.sql`：2 张表 + M/C/F 菜单 + admin 授权。
- 应用配置管理页后端 CRUD（密文存储、不回显、留空沿用）+ 前端页面。
- **验收标准**：配置页可保存钉钉凭据，列表页 secret 列显示 `******`，编辑留空保存后原密文不变。

### 阶段 2：钉钉连接器实现（4~5 天，含考勤同步核心场景）

- `DingTalkConnector implements IExternalConnector`：
  - access_token 获取 + Redis 缓存（有效期 2h，提前 10 分钟刷新，失败重试 1 次）；
  - 工作通知（`message/corpconversation/asyncsend_v2`）；
  - 待办创建（`todo/tasks/create`）；
  - 连接测试（发送一条测试工作通知给配置人）。
- 平台用户 ↔ 钉钉 userId 映射表 `integration_user_binding`（user_id, connector_type, external_user_id，同步时维护）。
- 通讯录同步 Quartz 任务（`integrationContactSyncTask`）。
- **考勤数据同步（核心场景，§3.7）**：`integrationDingtalkAttendanceTask` 每日拉取钉钉打卡 → 转 `HrAttendanceImportDTO` → 复用 `importAttendance` 幂等导入；考勤记录页"从钉钉同步"手动补拉按钮（hr 模块加 1 个 F 权限 + 1 个接口）。
- **验收标准**：管理页点"连接测试"收到钉钉工作通知；通讯录同步任务手动触发一次全量成功并生成映射；昨日钉钉打卡 T+1 自动出现在考勤记录且来源为"钉钉"，与 Excel 导入通道结果一致；未匹配员工进入异常清单。

### 阶段 3：回调与业务联动（1~2 天）

- `IntegrationCallbackController` + 钉钉验签解密。
- 业务联动试点：审批类事件（如采购审批通过）通过 `IExternalConnector.sendWorkMessage` 推送钉钉通知——选 1 个最小业务场景（建议：供应商审核结果通知）打样。
- **验收标准**：回调验签通过、日志表可查；试点业务场景端到端通知到达。

**一期合计：约 1.5~2 周（含联调）。**

## 五、二期预留：企业微信（3~5 天）

- `WecomConnector implements IExternalConnector`：corpid + corpsecret + agentid 换 token，工作通知 `message/send`，结构与钉钉近乎同构。
- 配置表、管理页、日志、任务**全部零改动复用**——这是抽象层价值的直接证明。
- 回调验签复用同一 Controller 路由。

## 六、三期（暂缓）：用友 / 金蝶

- 暂缓理由：版本碎片化（用友 U8/T+/U8C/YonBIP 多体系、金蝶 WISE vs 云星空），且无当前客户场景牵引；贸然实现会造出无真实需求的抽象。
- 预留：`connector_type` 字段已含 `yonyou/kingdee`；`IExternalConnector` 后续可扩展 `syncVoucher`（单据同步）等 default 方法，不影响已有实现。
- 重启条件：出现真实客户场景 → 先做该客户版本适配器 → 再抽象。

## 七、风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 回调需公网 HTTPS | 中 | 一期核心场景（通知/待办/通讯录）均为外发，不依赖回调；内网客户走轮询兜底 |
| token 并发刷新冲突 | 低 | Redis 缓存 + 单机锁；分布式部署时用 setnx |
| AppSecret 泄露 | 高 | 密文存储 + 不回显 + 操作日志 + 仅管理员可见（与账号安全规范一致） |
| 通讯录同步误覆盖平台数据 | 中 | 映射表只补外部 ID，不触碰角色/权限/部门归属；同步前备份差异报告 |
| 业务模块依赖方向被破坏 | 中 | 强制业务侧只依赖 common 接口，评审时检查 import |
