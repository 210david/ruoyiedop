## 0 结论先行

**可行性结论**：技术上可行，但现有架构**不能「直接打通」上线**。知识库链路（抽取→切片→向量→检索→带引用问答）已跑通，业务侧也有清晰接入点；阻塞点不在「能不能同步」，而在「同步之后权限、可恢复性、可观测性、可验收性是否成立」。

**本轮评审结论**：上一版方案 C「统一附件注册＋事件驱动异步＋引用式索引」**架构主干成立，但不足以作为开发依据**——十维度完整 2 / 部分 5 / 缺失 3；存在 **1 处与已核实事实的硬冲突**（过滤后置 vs 全局助手全库可见）与 **3 类会让历史两起 P0 事故重演的缺口**（原文件丢失、embedding 切换检索全空、删除无事务）。根因是原方案只写了「数据链路」，缺「可观测 / 可恢复 / 可重建 / 可验收 / 用户可承接」五条落地腿。

**推荐方案**：保留方案 C 主干；P0 由「安全底座」重定义为「**安全底座＋可恢复性＋可重建性准入**」；补上过滤前置、源生命周期契约、索引版本化与回滚、埋点与基线、运维与用户侧承接后分阶段落地。

**纪律红线**：**P0（含 8 项前置任务）未完成前，不得把任何业务附件接入生产知识库。** 现有检索 SQL 在全局助手不带 module 时全库可见，标书、报价、合同一旦进入切片表即为可直接复现的越权泄漏。

**量化概览**：P0 前置任务 **8** 项、P0 代码交付 **11** 项（v1.3 分支 B 新增 P0-11 OCR/图片解析 XL 级）、P1 **13** 项、P2 **5** 项；**v1.4 静态核验使 R19「多拦截点」转强制、且「换版留历史行」需新增字段并改业务保存逻辑，P0 工作量进一步上调·需工程复核**；待确认原 **23** 条＋v1.3 派生 **1** 条，逐项状态见 **§0.1 台账**（「18 条／20 条」混用口径作废）；上一版 **15–25 人日粗估不成立**，需重估；分支 B 使 **P1 顺延约 1–2 个迭代波次**。

**v1.3 客户口径已确认 5 项（2026-11-09 逐条确认，主理人一次性汇编）**：① R18 **分支 B**——投标扫描件／盖章件须能全文检索；② **仅报价／涉密件不得外送**外部 embedding/LLM（分级拦截＋审批留痕，P0-10 由条件性转正式）；③ 跨项目回跳**沿用现有附件权限**，保留可见／可预览／可下载三级；④ 客户指定一位验收人、**上线当天抽查通过即认账，不设验收观察期**；⑤ 附件**上传后默认自动纳入**，可撤回／排除。**v1.4 收敛**：② 进一步定为「报价/涉密件**一律不纳入、只登记**」，P0-10 简化为密级初筛＋登记＋拦截外送，**免本地向量化、免审批放行流**；以 §0.1 台账 A3 为准。

| 文件格式兼容 | ⚠️部分 | 扫描件不支持（F4）；投标扫描件占比未知（A5）；P1 静默空切片致验收不达标 | P1 扫描件探测＋显式不可检索标记；OCR 试点按 M1 条件触发；验收书面限定可解析附件（R7）。**v1.4 注记：本节是对「上一版方案」的评审记录；现行排期以 §5.3／§6 为准——客户已选分支 B，OCR 首次引入已升 P0-11（XL），报价／涉密件不识别、只登记** |

| 性能与成本 | ⚠️部分 | O(N) 全量捞取与覆盖率↑直接冲突；`new Thread` 无池；无成本/重建耗时护栏；无压测对照 | 候选上限、有界线程池、成本护栏、×10 压测、上传成功率对照组（R8） |
| 对现有模块侵入性 | ❌需修正 | 「不改上传交互」与上传者知情/控制冲突；用研 8 场景 3 项空白 | **不改上传流程**，改在附件列表与检索结果侧承接（R4）；P0 代码与前置任务严格分离（R1） |
| 可观测与验收 | ❌缺失 | P0 无埋点→P1 指标全不可衡量；分母/起算/负向/对照组全缺；越权=0 可被「一律拒绝」达成；回跳鉴权失败率在 P0 前分子分母都不存在 | E1–E4 埋点前置 P0；M1–M6 基线单列工时；新增「可采集起点」；负向用例集＋配对观测（R8） |

统计：**完整 2 / 部分 5 / 缺失 3**。F 类通行做法（Outbox 同事务＋幂等、过滤前置、事件重放与全量重建、删除事务化）写**强制约束**；I 类（生命周期契约形式、四维灰度、重刷矩阵）写**设计待决项**；H 类（扫描件占比、验收口径）写**待客户确认项**，不得落成硬性验收数字。

### 2.2 上一版未识别的 7 个关键缺口

| # | 缺口 | 为何致命 |
|---|---|---|
| G1 | **过滤位置错误**（未识别 pre-filter 必要性） | 现状全量捞取后置过滤＝全库可见（F2）＋越权切片入算分/日志；未来 ANN 下推不可平移 |
| G2 | **指标可采集起点时序** | 回跳二次鉴权链路当前不存在，P0 前分子分母取不到；deny 不埋点则分子恒 0、指标反而美化 |
| G3 | **引用索引的源生命周期契约** | 引用不复制二进制 ↔ 根路径分叉致原文件全丢（F6①）→「命中却打不开」的孤儿切片 |
| G4 | **删除事务化** | 删 doc 与删 chunk 无事务（F3）＝孤儿切片成因 |
| G5 | **索引版本化／重建回滚／零召回归因** | embedding 切换致检索全空（F6②）会重演；只设绝对阈值无法归因 |
| G6 | **Outbox 仅增量＋对账双路径缺失** | 存量、散字段 URL、导入/接口旁路不触发事件 → 上线即「半库可检索」 |
| G7 | **用户侧承接与验收可签收性** | 知情/控制、空结果求助、审计、运维人工面全空白；无基线无用例集则覆盖率与越权=0 无法签字 |

### 2.3 裁决：保留 5 / 修正 7 类

**保留**：① Outbox 与业务同事务＋异步 Worker（消除双写不一致与同步阻塞）；② 统一注册＋只读适配器保「业务零侵入」；③ 引用式索引＋缺省拒绝 scope＋回跳二次鉴权（须配 R3 契约）；④ content_hash＋唯一键幂等＋版本切换；⑤ P0 先底座、Non-goals 克制。

**修正**：P0 重定义（R1）／过滤前置（R2）／源生命周期契约与删除事务化（R3）／Non-goals 细化（R4）／backfill 与旁路（R5）／索引版本化与重建（R6）／OCR 与验收口径（R7）。

### 2.4 四条实现路径对比（含本轮裁决）

| 路径 | 核心做法 | 优点 | 缺点 | 侵入性 | 结论 |
|---|---|---|---|---|---|
| A 上传入口全局拦截 | 在 CommonController 切面把每个上传文件直接写知识库 | 一处改动覆盖全模块 | 误纳（图片/临时文件）、无业务元数据与权限上下文、同步解析拖慢上传、接不住散字段与存量 | 极低 | 只能作**采集触发器**，不可单独成案 |
| B 逐业务模块显式改造 | 在 pjm/bid 附件 Service 调知识库 Service | 元数据/权限上下文最完整 | N 模块×M 入口重复、与业务耦合、随模块线性增长、易漏接 | 高 | 适合试点，不宜作平台方案 |
| **C 统一注册＋事件驱动异步引用式索引** | 注册事件与业务同事务 → Worker 去重/继承/抽取/切片/向量化 → 引用原文件不复制 | 业务零侵入、异步不阻塞、幂等/重试/对账有锚点、可按白名单灰度、权限统一收口 | 最终一致（分钟级）；需新增任务表与调度；抽取接口须改 InputStream；检索层必须同步改造 | 低 | **推荐主方案（按 R1–R23 修正后）** |
| D 检索时联邦/旁路 | 不预建索引，问答时实时拉取或仅返回标题命中＋原文跳转 | 零索引成本、无一致性问题、最快上线 | 无全文语义检索、大文件实时解析不可行、不满足客户真实诉求 | 极低 | 仅作过渡降级或引用回跳补充 |

**采集触发机制**：采用「统一上传切面＋附件表只读适配器」双通道；不推荐纯定时全量扫描（感知不到删除、反复全表扫描）与 binlog/CDC（当前私有化单机部署引入运维面）。对账 Job 只做兜底修补，不作主链路。

## 4 开发方案 · 功能规格（v1.1 核心）

### 4.1 问题陈述、目标与非目标

**问题**：业务模块附件只能在「AI 知识库专属页」二次上传后才可检索，造成重复劳动与资料缺口；而现状检索层仅按 module 字符串隔离、全局助手不带 module 时返回全库切片（F2），直接纳入将造成投标报价、合同等高敏附件越权可见。本质不是「补一条同步链路」，而是把「专属页封闭语料」扩成「全业务附件开放语料」后的**权限面、源生命周期、可恢复性、可验收性**四个系统性问题。

**目标**：一次上传即可检索｜业务零侵入｜检索可见范围严格等于业务权限｜索引可恢复/可重建/可回滚｜全链路可观测、可验收、可签收。v1 交付安全底座＋两模块灰度＋治理闭环；**v1.4 分期订正**：分支 B 后 OCR/图片解析已前移至 **P0-11（属 v1 期内）**，向量索引/ANN 评估、历史回溯与存量全量回填仍留 P2；报价／涉密件一律只登记、不识别、不向量化。

**非目标**：不改上传流程交互（改在附件列表与检索侧承接）；不复制二进制原文件；**不做全量敏感等级定级审批流**（v1.4：报价／涉密件按「只登记」处置，无须审批放行流）；**不做涉密件 OCR/向量化**（v1.4 客户口径）；不做实时秒级索引/跨租户/ANN 引擎/逐模块显式改造/**单独上线公告**；不把未确认策略写成既定策略；不用单一覆盖率签收 2×2 四象限。

### 4.2 用户故事（均为推断/假设，无访谈佐证）

| ID | 角色 | 故事 |
|---|---|---|
| US1 | 投标专员 | 希望上传后看到「是否已纳入、谁可检索到」并能单文件排除/撤回纳入，避免报价在不知情下被全库检索 |
| US2 | 保密责任人 | 希望高敏附件纳入前审批、定级、外送拦截且留痕（**v1.4 已收敛**：客户确认报价／涉密件「一律不纳入、只登记」——P0-10 简化为密级初筛＋登记＋拦截外送，免审批放行流；普通件不做全量定级） |
| US3 | 项目经理 | 希望单据作废/附件撤回后不再被检出或明确标注「已失效」 |
| US4 | 知识库管理员 | 希望在一个视图看失败原因、单条/批量重跑、人工排除、裁决对账差异并留痕 |

### 4.3 状态机与业务事件→索引动作

**索引状态机**：`REGISTERED → QUEUED → PARSING → {PARSED | NO_TEXT_LAYER | NOT_INDEXABLE | UNSUPPORTED | FAILED} → EMBEDDING → INDEXED → {SUPERSEDED | INVALID | DELETED(软删)}`；`FAILED → RETRY(n) → DEAD_LETTER → 人工重跑`。`NOT_INDEXABLE`/`UNSUPPORTED` 为**终态非失败态**，不计入失败率与报障量。

**业务事件映射**（v1.4：换版口径已由客户确认、字段现状已静态核验）：撤回/废标/单据作废/`delFlag` 软删 → 立即下线或 INVALID；换版 → 旧版 SUPERSEDED＋`superseded_by`/`doc_version`/`invalid_ts`，检索默认只返最新有效版；权限回收 → 实时鉴权＋对账补跑（归④越权窗口）；文件 404 → 引用完整性校验标失效＋告警（归物理孤儿）。**v1.4 订正**：客户确认「留历史行、只返最新有效版」，但附件表**无 version／状态枚举**、单条编辑物理覆盖（§1.3），故本映射须**新增字段并改业务保存逻辑**才能实现，不得按代码现状静默实现；语义失效**阈值仍不设**（R15）。

### 4.4 数据模型改造（**数据结构变更，非纯埋点**，须单列工时/回归/存量兼容）

### 4.6 检索层改造点（**F 类强制约束**）

1. **废止**「全部切片无 LIMIT 捞到应用层算分再后置过滤」；`module＋数据权限＋（预留 sensitivity）` 过滤**前置到候选集/Top-K 之前**，加 LIMIT/候选上限；越权切片不得进入算分与日志。
2. 全局助手入口**强制 scope、缺省拒绝**；不带 scope 请求计入 P0 哨兵。
3. `selectDocByName` 按文件名查重停用，改 source 唯一键＋content_hash；删 doc/chunk/向量/引用须事务化或补偿事务。
4. 所有附件读取出口统一鉴权（R19），非单一拦截点；出口清单列为验收项。**v1.4 静态核验已确证旁路出口存在**（`/ai/knowledge/download/{docId}`、`/preview/{docId}`），本条为**强制 P0**，不再按「核实无旁路可收敛单点」的条件分支处理。
5. 未来引入 ANN 须把过滤下推引擎层，SQL 层方案不可平移。

### 5.1.1 门禁定位裁决（主理人，2026-11-09）

规划师回传核对时提出一处实质冲突：R13 把故障注入定为「P1 上线门禁」，而需求分析师把它与「全量重建/回滚/reindex」一并定为「P1 灰度准入」。主理人裁决**拆分处理，不二选一**：

| 项目 | 定位 | 理由 |
|---|---|---|
| 故障注入三项＋全量重建/回滚/reindex **实现与演练** | **P1 灰度准入 Gate** | 二者验证的是 P0 已交付的安全与可恢复能力（删除事务化、版本化/别名/回滚点、P0 哨兵），必须在**首次真实用户暴露前**证明有效；R1 亦明确「全量重建/回滚实现是 P1 灰度准入条件，非 P0 代码」。据此**修订 R13 中「上线门禁」口径为「灰度准入」**，属主理人裁决更新，非执行错误 |
| 切片 ×10 压测 | **P1 上线门禁（W7）** | 容量验证依赖 P1 适配器产生的真实切片量，置于全量上线前更合理 |

**顺延影响**：Gate 加厚约 1 个 M 级演练量；因演练对象是 P0 能力、可与 P0 收尾并行准备，**不构成无条件 1 个迭代波次顺延**；仅当 P0 哨兵/版本化/事务化未按时就绪才顺延。
**同时订正**本汇编引入的一处矛盾：Gate 原写「重建/回滚演练可用」而实现排在 W7 —— 现统一为「实现与演练均在 Gate 前完成」，W7 只保留 ×10 压测与灰度观察结论。
**四项低风险补丁一并采纳**：①「语义失效事件来源＋死信/事件丢失检测」并入 **P0-02 验收门槛**，不新增交付项、不重估工期（v1.1 不改变 §3 分期与项数的口径维持）；② 门禁按「可立验收条款／可签收」两栏理解；③ §2.7 引用替换为 **AC-12/AC-13**；④ 报障入口最小自述原因与最小可理解性选项落到 **P1-09 验收门槛**。

### 5.2 结论先行

- 【事实】**P0 被重定义**：由「安全底座」扩为「安全底座＋可恢复性＋可重建性准入」（R1）。P0 doc 字段改造属**数据结构变更**（F1），叠加 12 类以上埋点字段、M1–M6 基线采集、读取出口统一鉴权（R19）与 8 项阻塞式前置任务——这些在上一版 15–25 人日粗估时**均不在覆盖范围**（F9）。
- 【推断】**15–25 人日为何低估**：该估算对应「一条增量同步链路」，现 P0 是「安全改造＋数据结构迁移＋可观测体系＋可恢复契约」四条并行工作流；粗估只含写代码，不含前置任务、存量兼容、回归、演练与验收。属**范围性缺口，非系数偏差**，故不沿用、不换算人日。
- 【推断＋v1.4 更新】**最大排期风险不是代码量，而是关键路径上的外部决策与工程核验**：原列 R18 分支 A/B、书面验收口径、状态枚举/换版、旁路读取接口、评测集/签收方，任一悬空都会阻塞 P1 灰度准入。**v1.3：R18 已定分支 B**（OCR 升 P0-11、P1 顺延 1–2 波次）；**v1.4：OCR 外送合规、涉密件处置、密级判定、换版、对账、生命周期、灰度、排除清单、评测集、组件许可共 15 项口径已逐条确认，A2/A3/A4 工程静态核验已完成**；风险重心收敛为 ① **验收人姓名／岗位＋负向权限用例集客户确认＋三项基线数据**，② **生产运行时回传 10 项**，③ **换版改造与多拦截点治理按 R1 判定是否新增 P0 交付项**；任一未齐仍阻塞 P1 灰度准入。
- **给客户一句话**：「先做实『谁看得见、删得干净、能重建、能验收』四件底座并书面确认验收口径，再谈业务附件自动可搜；**扫描件要不要全文可搜这个决定，会直接改变第一期的范围和时间表**。」
