## 零、本次要解决的问题（先读这一节）

本次部署要解决两件事，**第一件是阻塞项，必须优先处理**：

| 优先级 | 问题 | 现象 | 影响 |
|--------|------|------|------|
| **P0（阻塞）** | 知识库文档**原文件全部丢失** | 下载原文件报「原文件已丢失，请重新上传」 | 预览、下载功能不可用；即使部署新版本也无法预览 |
| **P1** | 后端/前端**未更新到最新版本** | `/prod-api/ai/knowledge/preview/{docId}` 返回「系统处理异常」 | docx 预览仍是旧的前端渲染，表格错乱、版式失真 |
| **P2** | LibreOffice **未确认是否安装** | 无法判定（因 P1 接口未部署） | 若未安装，Office 文档预览将回退到前端渲染 |

> **线上实测证据（2026-09-20）**：
> - `GET /prod-api/ai/knowledge/doc/11` → 200 正常（老接口可用）
> - `GET /prod-api/ai/knowledge/chunks/11` → 200 正常（老接口可用）
> - `GET /prod-api/ai/knowledge/preview/11` → `{"msg":"系统处理异常，请联系管理员","code":500}`（**新接口不存在**）
> - `GET /prod-api/ai/knowledge/download/{11,6,2,7}` → 全部「原文件已丢失，请重新上传」

## 二、P0：排查并修复原文件丢失

### 2.1 第一步：确认文件是否真的丢失

登录服务器，执行：

```bat
REM 确认配置中的上传根目录（应为 D:/EDOP/uploadPath）
type D:\EDOP\app\application.yml | findstr /C:"profile"

REM 查看知识库文档实际存放目录
dir D:\EDOP\uploadPath\ai\knowledge
```

**分支 A：目录为空或不存在** → 文件确实丢失，跳到 **2.3 重新上传文档**

**分支 B：目录里有文件** → 文件在，是**路径配置不匹配**，进入 2.2

### 2.2 分支 B：路径配置排查

**核对数据库记录的路径**：

```bat
D:\EDOP\mysql\bin\mysql.exe -uroot -p ry-vue -e "SELECT doc_id, doc_name, file_path FROM ai_knowledge_doc;"
```

**核对应用配置的上传根目录**：

```bat
type D:\EDOP\app\application.yml | findstr /C:"profile"
```

> ✅ **本环境实际情况**：生产服务器上传根目录为 **`D:/EDOP/uploadPath`**，
> 文件实际存放于 `D:\EDOP\uploadPath\ai\knowledge\`。
>
> ⚠️ **排查提示**：项目源码/部署模板中 `profile` 的默认值为 `D:/ruoyi/uploadPath`。
> 若服务器上的 `application.yml` **未同步改回** `D:/EDOP/uploadPath`（例如更新版本时被新配置覆盖），
> 就会出现「配置指向 `D:\ruoyi\uploadPath`、文件却在 `D:\EDOP\uploadPath`」的分叉，
> **表现为接口报「原文件已丢失」但文件其实还在** —— 这正是本次要重点排除的情况。

**比对规则**：数据库 `file_path` 是**相对路径**（如 `ai/knowledge/1789907361338_xxx.docx`），
实际文件应在 `profile 配置值 + file_path`，即 `D:\EDOP\uploadPath\ai\knowledge\1789907361338_xxx.docx`。

| 情况 | 处理方式 |
|------|----------|
| 配置被改成了 `D:/ruoyi/uploadPath`，文件在 `D:\EDOP\uploadPath` | **改配置**：把 `D:\EDOP\app\application.yml` 中 `profile` 改回 `D:/EDOP/uploadPath`，重启后端 |
| 文件确实在 `D:\EDOP\uploadPath` 且配置正确，但接口仍报丢失 | 检查 `ai\knowledge` 子目录及文件是否真实存在，核对数据库 `file_path` 记录 |
| 数据库 `file_path` 记录错误 | 按实际文件名修正 `file_path`（见下方 SQL） |

> **优先动作**：先执行 `type D:\EDOP\app\application.yml | findstr /C:"profile"`，
> 若输出不是 `D:/EDOP/uploadPath`，**改配置即可修复，无需重新上传文档**。

**修正 file_path 示例**（仅在确认文件名后执行）：

```sql
-- 先查询确认
SELECT doc_id, doc_name, file_path FROM ai_knowledge_doc WHERE doc_id = 11;
-- 再更新（示例，请按实际文件名替换）
UPDATE ai_knowledge_doc SET file_path = 'ai/knowledge/实际文件名.docx' WHERE doc_id = 11;
```

### 2.3 分支 A：重新上传文档

原文件丢失后**无法恢复**，需重新上传。注意：

- ✅ **知识库问答不受影响**：切片内容存在数据库 `ai_knowledge_chunk` 表，问答功能正常
- ⚠️ **重新上传会产生重复文档**：建议先删除旧文档记录再上传，避免列表出现重复项

**操作步骤**：

1. 在系统「AI 知识库」页面，删除原文件已丢失的文档记录（删除会连带清理切片）
2. 重新上传原文件（`docx` / `pdf` / `md` / `txt`）
3. 上传后确认列表状态为「解析成功」、切片数正常

> **重要**：重新上传的文档会自动触发**异步预转换**（新版本功能），上传完成后 PDF 预览缓存即已就绪，用户首次点击预览无需等待。


```bat
dir D:\EDOP\app\ruoyi-admin.jar
```

```bat
REM 清空旧文件
```

## 四、P2：LibreOffice 安装与配置

### 4.1 判断是否需要安装

部署完新版本后，用下面任一方式判断：

**方式 1：看后端启动日志**

```bat
type D:\EDOP\app\logs\winsw\EDOP-Backend.out.log | findstr /C:"LibreOffice"
```

| 日志内容 | 含义 |
|----------|------|
| `LibreOffice 转换程序: xxx\soffice.exe` | ✅ 已找到，无需安装 |
| `未找到 LibreOffice(soffice)，Office 文档将使用前端渲染预览` | ❌ 需安装（见 4.2） |

**方式 2：接口验证**（见第六节验证清单）

### 4.2 安装 LibreOffice

**推荐：便携化安装到 `D:\EDOP\LibreOffice`**（与 JDK/MySQL 等保持目录统一）

1. 下载 Windows x86-64 版安装包：https://www.libreoffice.org/download/
2. 运行安装程序 → 选择「自定义安装」
3. 安装路径改为 `D:\EDOP\LibreOffice`
4. **取消勾选**「创建桌面快捷方式」「随系统启动快速启动器」（服务器上不需要）
5. 完成安装，确认文件存在：

```bat
dir D:\EDOP\LibreOffice\program\soffice.exe
```

### 4.3 配置 SOFFICE_PATH

> **说明**：代码会自动探测 `C:\Program Files\LibreOffice`、`D:\Program Files\LibreOffice`、
> `E:\DevTools\LibreOffice`、`D:\DevTools\LibreOffice` 等常见路径。
> 若安装在上述路径，**无需配置**；安装在自定义路径（如 `D:\EDOP\LibreOffice`）则需配置。

**方式一：改 WinSW 服务配置（推荐，只影响后端服务）**

编辑 `D:\EDOP\service\edop-backend.xml`，在 `<service>` 标签内添加一行：

```xml
  <env name="SOFFICE_PATH" value="D:\EDOP\LibreOffice\program\soffice.exe" />
```

**添加位置示例**（放在 `<workingdirectory>` 之后即可）：

```xml
<service>
  <id>EDOP-Backend</id>
  <name>EDOP 后端服务</name>
  <executable>%JAVA_HOME%\bin\java.exe</executable>
  <arguments>... -jar ruoyi-admin.jar</arguments>
  <workingdirectory>D:\EDOP\app</workingdirectory>
  <env name="SOFFICE_PATH" value="D:\EDOP\LibreOffice\program\soffice.exe" />   <!-- 新增这一行 -->
  <logpath>D:\EDOP\app\logs\winsw</logpath>
  ...
</service>
```

**方式二：改 `env.bat`（全局生效，供脚本调用）**

编辑 `D:\EDOP\scripts\env.bat`，在「Component Paths」区块追加：

```bat
REM ===== LibreOffice（Office文档转PDF预览）=====
set SOFFICE_PATH=%EDOP_HOME%\LibreOffice\program\soffice.exe
```

> ⚠️ 注意：WinSW 服务**不会自动读取** `env.bat`，若用方式二，需确保服务启动脚本已加载该文件。
> **建议直接用方式一**。

### 4.4 应用配置并重启服务

修改 `edop-backend.xml` 后**必须重装服务**才能生效：

```bat
D:\EDOP\service\edop-backend.exe stop
D:\EDOP\service\edop-backend.exe uninstall
D:\EDOP\service\edop-backend.exe install
D:\EDOP\service\edop-backend.exe start
```

### 4.5 创建转换缓存目录

```bat
REM 转换缓存目录位于上传根目录下
mkdir D:\EDOP\uploadPath\convert
```

> 代码会自动创建，但预先建好可避免首次转换时的权限/时序问题。

### 4.6 手动验证转换工具可用

```bat
REM 用知识库里任一 docx 文件测试（文件名按实际替换）
"D:\EDOP\LibreOffice\program\soffice.exe" --headless --norestore --convert-to pdf --outdir D:\temp_test "D:\EDOP\uploadPath\ai\knowledge\某个文档.docx"

REM 检查产出
dir D:\temp_test
```

> ✅ 看到 `.pdf` 文件即工具可用。
> ⚠️ 首次运行可能较慢（10~30 秒，LibreOffice 初始化用户配置），属正常现象。
> 若报错，尝试先手动运行一次 LibreOffice 图形界面再关闭，让配置初始化完成。

## 四点五、P3：上传路径配置（新增功能）

> 本节为新增功能说明。若服务器**暂时不需要修改上传路径**，可跳过本节，但**强烈建议执行 4.5.1 的 SQL 脚本**，以获得「配置被误覆盖时启动即报错」的保护能力。

### 4.5.1 执行初始化 SQL（必做）

新版本引入了两个配置项/菜单，需在数据库中执行（脚本已放在 `deploy/config/sql/`，**幂等，可重复执行**）：

```bat
REM 1. 插入上传路径配置项（system.upload.path）
D:\EDOP\mysql\bin\mysql.exe -uroot -p --default-character-set=utf8mb4 ry-vue < D:\EDOP\config\sql\add_upload_path_config.sql

REM 2. 插入「上传路径配置」菜单及权限
D:\EDOP\mysql\bin\mysql.exe -uroot -p --default-character-set=utf8mb4 ry-vue < D:\EDOP\config\sql\add_upload_path_menu.sql
```

**验证 SQL 已生效**：

```bat
D:\EDOP\mysql\bin\mysql.exe -uroot -p ry-vue -e "SELECT config_key, config_value FROM sys_config WHERE config_key='system.upload.path';"
D:\EDOP\mysql\bin\mysql.exe -uroot -p ry-vue -e "SELECT menu_id, menu_name, perms FROM sys_menu WHERE perms LIKE 'system:uploadPath%';"
```

预期：各返回 1 条配置 + 3 条菜单权限记录。

> ⚠️ **配置值请改为你的实际路径**：脚本默认写入 `D:/EDOP/uploadPath`，若与实际不符请修改脚本后再执行，或在页面上直接改（见 4.5.3）。

### 4.5.2 路径配置优先级（理解后再操作）

上传根目录现在支持三级配置，**优先级从高到低**：

| 优先级 | 配置方式 | 说明 |
|--------|----------|------|
| 1（最高） | 环境变量 `EDOP_UPLOAD_PATH` | 适合容器化/多环境；**设置后页面修改不生效** |
| 2 | 数据库配置 `system.upload.path` | 管理端页面可改，**保存即时生效，无需重启** |
| 3（最低） | 配置文件 `application.yml` | 兜底默认值 |

> **本次升级的默认行为**：若数据库配置存在，启动时会**优先采用数据库配置**并覆盖 `application.yml` 的值。
> 这解决了「配置文件被新版本覆盖导致路径回退」的历史问题。

### 4.5.3 管理端配置页面

**入口**：系统管理 → 上传路径配置

**页面能力**：

| 功能 | 说明 |
|------|------|
| 当前生效路径 | 显示实际生效的路径 |
| 配置来源 | 环境变量 / 数据库配置 / 配置文件（一眼看出谁在起作用） |
| 目录状态 | 存在且可写 / 不可写 / 不存在 |
| 目录占用 | 文件数 + 总大小（评估迁移体量） |
| 修改路径 | 校验绝对路径、拦截系统目录、自动创建、**保存即时生效** |
| 文件迁移 | 把旧目录文件迁移到新目录，同大小文件自动跳过 |

**修改路径的正确操作顺序**（**顺序错误会导致历史文件读取失败**）：

1. 页面填入新路径 → 点「保存并生效」（新目录自动创建）
2. 页面「文件迁移」区域 → 源目录填**旧路径** → 点「执行迁移」
3. 验证功能：打开任一知识库文档，能正常下载/预览
4. 确认无误后，自行清理旧目录（**迁移不会删除源目录**）

### 4.5.4 启动自检（本次升级的重要保护）

新版本启动时会自动校验上传根目录：

| 情况 | 行为 |
|------|------|
| 目录不存在 | **自动创建** |
| 目录不可写 | **启动失败并输出明确错误，进程退出** |
| 路径被文件占用 | 启动失败并报错 |

**这样设计的目的**：避免「配置指向 A、文件在 B」时程序仍正常启动，等到用户上传/预览才暴露问题。

**自检日志示例**：

```
上传根目录自检通过: D:/EDOP/uploadPath（来源: 数据库配置 system.upload.path）
```

**自检失败示例**（此时服务不会起来）：

```
上传根目录自检失败，程序退出: [EDOP启动自检] 上传根目录不存在且无法创建: Z:/xxx，
请检查磁盘/权限，或修改 ruoyi.profile / 设置环境变量 EDOP_UPLOAD_PATH
```

> ⚠️ **排障提示**：若服务启动后立刻退出，**先查这条日志**，多数是上传路径配置错误。

### 4.5.5 环境变量方式（可选，适合容器/多环境）

若需用环境变量强制指定路径，编辑 `D:\EDOP\service\edop-backend.xml`，在 `<service>` 内添加：

```xml
  <env name="EDOP_UPLOAD_PATH" value="D:/EDOP/uploadPath" />
```

改完**必须重装服务**：

```bat
D:\EDOP\service\edop-backend.exe stop
D:\EDOP\service\edop-backend.exe uninstall
D:\EDOP\service\edop-backend.exe install
D:\EDOP\service\edop-backend.exe start
```

> 设置环境变量后，管理页面的「修改路径」会**自动禁用**并提示原因，避免误操作。

## 五、常见问题排查

| 问题 | 原因 | 解决 |
|------|------|------|
| 替换 jar 报 `Unable to rename ... .jar.original` | 后端进程仍占用 jar | 先 `stop` 服务并确认 `netstat` 无 8004 监听 |
| 启动报 `Port 8004 was already in use` | 旧进程未退出 | `netstat -ano \| findstr :8004` 找 PID → `taskkill /PID xxx /F` |
| 预览接口返回 `文档转换预览失败` | LibreOffice 未装/路径错 | 按第四节配置 `SOFFICE_PATH` 并重装服务 |
| 预览接口返回 `原文件已丢失` | 源文件缺失 | 按第二节排查，必要时重新上传 |
| 预览接口返回 `该格式不支持服务端转换预览` | 文件类型不在支持列表 | 支持 doc/docx/xls/xlsx/ppt/pptx/rtf/odt/ods/odp；txt/md/pdf 走原有逻辑 |
| 预览接口返回 `系统处理异常` | 新版本未部署成功 | 确认 jar 已替换、服务已重启 |

## 八、部署注意事项汇总

1. **必须先停服务再替换 jar**，否则 jar 被占用导致替换失败
2. **原文件丢失是本次部署的前置阻塞项**，不解决则预览功能无法验证
3. **LibreOffice 未安装不影响系统可用性**：代码已做降级，会自动回退到前端渲染，只是预览效果差
4. **服务器内存建议 ≥ 4GB**：LibreOffice 单次转换约占 100~200MB（转换完即释放，无常驻）
5. **Nginx 超时配置**：`proxy_read_timeout 120s`，与转换超时一致；若文档特别大建议调大到 300s
6. **转换缓存会自动维护**：源文件更新（时间戳变化）时缓存自动失效重转，无需人工清理
7. **首次转换较慢**：服务器上首次运行 LibreOffice 需初始化配置，可能 10~30 秒，后续正常
